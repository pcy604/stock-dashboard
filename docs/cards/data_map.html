화면에 뜨는 숫자가 어느 파일에서 왔고, 그 파일을 누가 언제 만드는지. 그리고 왜 자꾸 조용히 깨지는지.

전체 흐름

형 질문: 같은 데이터를 여러 곳에서 가져와 느려지지 않나

답 — 중복은 있지만 병목은 아니다

대시보드가 읽는 results/*.json 18개를 전부 파싱해도 543ms다. 대시보드는 market.db를 아예 열지 않는다(DB 접근 0회). 무거운 건 발행 쪽이고, 화면 쪽은 이미 가볍다.

us_shares.csv 가 매주 통째로 바뀐다

299,001행짜리 CSV인데 as_of 컬럼이 모든 행에 있어 갱신 때마다 전체가 diff로 잡힌다. 주당 15MB가 히스토리에 쌓인다. .git이 1GB까지 불었던 원인 중 하나다 (지금은 정리 후 338MB).

그래서 무엇을 할까

  • 안 한다 — 결과 JSON 통합. 300KB 아끼자고 파일 구조를 흔들 이유가 없다. 화면 로딩은 이미 543ms다.
  • 이미 했다 — CI 캐시. shares_cache·leaders_cache를 actions/cache로 붙였다. 1시간 47분짜리 재수집이 사라진다.
  • 이미 했다 — 폴백 판정. 파일 존재가 아니라 테이블 존재로 본다. 빈 DB가 폴백을 막던 문제.
  • 남았다 — us_shares.csv의 매주 전량 diff. as_of를 행마다 넣지 않으면 대부분의 행이 안 바뀐다. 다만 point-in-time 조회에 쓰이므로 스키마를 건드려야 한다 — 지금 급하지 않다.
이 지도가 말하는 진짜 교훈

느린 게 문제가 아니었다. 같은 코드가 로컬(DB 있음)과 CI(DB 없음)에서 다른 경로를 타는데, 그 갈림길이 조용히 끊긴다는 게 문제였다. 세 번의 사고가 전부 같은 자리에서 났다. 새 스크립트를 쓸 때마다 "이게 CI에서도 도는가"를 먼저 물어야 한다.
